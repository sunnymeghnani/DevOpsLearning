Blind spots in your notes
Seven things your write-up doesn't cover. Each one would have shortened the Apache and DNS investigation or will bite the Dokploy migration.
Uppercase words in commands (HOST, CONTAINER, POD, PORT) are placeholders.
No view of the packets
Your DNS flow infers where a query dies. A capture shows it directly: whether the query leaves the host, which server it goes to, and whether an answer comes back. Run it in one terminal while you repeat the failing curl in another.
sudo tcpdump -ni any port 53
Read: Let's learn tcpdump! [https://wizardzines.com/zines/tcpdump/] (free zine)
dig and curl don't take the same path
curl resolves names through glibc's getaddrinfo, which follows
/etc/nsswitch.conf
, so
/etc/hosts
and other sources count. dig skips all of that and asks the nameserver in
/etc/resolv.conf
directly. When the two disagree,
getent ahosts
is the one that matches what curl sees.
getent ahosts example.com
dig +short example.com
Read: Some things about getaddrinfo that surprised me [https://jvns.ca/blog/2022/02/23/getaddrinfo-is-kind-of-weird/] (Julia Evans)
Resolver logs are switched off
systemd-resolved can log every query, which upstream server it picked and why a lookup failed. Turn debug logging on, reproduce the failure, then turn it back off.
sudo resolvectl log-level debug
journalctl -fu systemd-resolved
sudo resolvectl log-level info
Read: Arch Wiki: systemd-resolved [https://wiki.archlinux.org/title/Systemd-resolved]
You can test past DNS without fixing it
--resolve
pins a name to an IP for one request and still sends the right SNI and Host header, so you can check Traefik and the app while DNS is broken. For plain HTTP, a Host header does the same job.
curl -v --resolve app.example.com:443:192.0.2.10 https://app.example.com/
curl -v -H 'Host: app.example.com' http://127.0.0.1/
Read: everything curl: Name resolve tricks [https://everything.curl.dev/usingcurl/connections/name.html]
Containers have their own resolver
On a user-defined network, which Compose and Dokploy create, a container asks Docker's embedded DNS at 127.0.0.11, and that forwards to the host's upstream servers. If Docker finds no usable upstream (a loopback-only resolv.conf, or a Docker-in-Docker CI runner), it falls back to 8.8.8.8 and 8.8.4.4, which on-prem firewalls usually block. Check from inside the container, and use netshoot when the image has no tools.
docker exec CONTAINER cat /etc/resolv.conf
docker run --rm -it --net container:CONTAINER nicolaka/netshoot
Fix: list your internal resolvers as
"dns": ["192.0.2.53"]
in
/etc/docker/daemon.json
and restart Docker.
Read: netshoot [https://github.com/nicolaka/netshoot] · Dokploy: Networking & DNS [https://docs.dokploy.com/docs/core/troubleshooting/networking]
Published ports skip UFW
A published port binds 0.0.0.0, and Docker's NAT rule rewrites the packet before UFW's rules ever see it, so
ufw deny
doesn't protect it. Your plan to avoid host ports is right. For temporary test ports, bind to loopback. Filtering that must apply to containers belongs in the
DOCKER-USER
chain.
ports:
- "127.0.0.1:18000:8000"
Read: Docker docs: Packet filtering and firewalls [https://docs.docker.com/engine/network/packet-filtering-firewalls/]
expose:
doesn't restrict anything
Containers on the same network can reach every port a process listens on, exposed or not.
expose:
works as a hint: Traefik uses an exposed port when you don't name one, and a wrong guess shows up as a 502. Isolation comes from which networks a container joins. In Compose, pin the port with a label.
traefik.http.services.app.loadbalancer.server.port=8000
Read: Traefik docs: Docker routing [https://doc.traefik.io/traefik/reference/routing-configuration/other-providers/docker/]

First moves

Network
Connection refused
versus
Connection timed out
First moves
sudo ss -ltnp 'sport = :PORT'
nc -vz HOST PORT
sudo tcpdump -ni any port PORT
Usual causes
Refused means a host answered with a reset: nothing listens on that address and port (often it's bound to 127.0.0.1 only), or a firewall rule rejects it. Timed out means packets vanish: a firewall drop, a wrong route, or a host that's down.
Read
Let's learn tcpdump! [https://wizardzines.com/zines/tcpdump/]
Network
Works on localhost, not from other machines
First moves
sudo ss -ltnp
sudo ufw status verbose
sudo nft list ruleset
Usual causes
The app listens on 127.0.0.1 instead of 0.0.0.0, a host firewall blocks the port, or a Docker port was published on 127.0.0.1 only (correct for anything that sits behind Traefik).
Network
mtr shows packet loss at a middle hop
First moves
mtr -rwn -c 100 HOST
Usual causes
Routers rate-limit ICMP replies addressed to themselves. Loss that doesn't carry through to the final hop isn't real. Only loss that persists to the last hop affects your traffic.
