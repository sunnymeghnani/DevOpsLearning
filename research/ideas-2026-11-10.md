# Ideas and enhancements (10 November 2026, written on Fable 5.2)

State when written: 123 map topics; 13 lab rooms, all L0; 12 decision drills; 74 topics have neither
a lab room nor a drill; Practice Arena 165 sites; page 15.72 MB (budget 15.95 MB, artifact limit 16 MB).
Pending from the checkpoint (recent_updated.md §20): pre-publish QA, artifact Version 11, more drills.

## Ranked

1. **Lab rooms for L1–L2, aimed at the gaps no free site covers.** Research on 9 Nov found no free
   practice anywhere for Dokploy, Docker Swarm break-fix, GRUB/boot recovery, SELinux/AppArmor
   troubleshooting, WireGuard, MTU problems, Jenkins, and Harbor (SadServers' Harbor room is paid).
   - Container-friendly first (current lab machine): systemd unit that keeps dying, journald/disk
     full, Apache vs another service on 443 (move to 81/444), nginx 502 vs 504, expired TLS cert,
     resolv.conf/systemd-resolved, cron job that never runs, sudoers lockout, logrotate, apt half-installed.
   - Needs the deferred KVM VM tier (kernel, nested Docker, NET_ADMIN): Swarm, Harbor, Dokploy,
     GRUB/fstab boot failure, WireGuard, MTU blackhole, AppArmor denials.
2. **Game-day mode.** A random room with only the symptom ("users report the site is down"), no
   task list, a timer, and the checks hidden until the end. This is the L4 exit test in roadmap.json
   and the "spin the wheel" idea from Wheel of Misfortune. SadServers checks with one script in the
   VM (`check.sh` → OK/NO); our rooms already have check scripts, so this is mostly UI.
   Optional: a 12-day "Advent" calendar of rooms + drills, like SadServers' Advent of Sysadmin.
3. **"Today" page: review queue + resume + progress.** 5–10 retrieval cards a day drawn from the
   460 Command Decoder cards, the interview questions and the lessons of drills already played
   (missed moves come back sooner). Spaced, with a simple 1-3-7-21 day schedule in localStorage.
   Evidence: retrieval practice and spacing are well supported; interleaving is mixed, so mix
   topics only lightly. Add Resume (last heading read) and per-level progress bars.
4. **AI tutor in the claude.ai copy only** (artifact capability `sample`, available on this account;
   `db` for cross-device progress, `dictation`/`tts` for spoken mock interviews, `downloads` for
   exports). Buttons: "Explain this command for my case", "Quiz me on this topic", "Review my
   incident note", "Mock interview (fresher/junior/senior)". The offline/Docker copy stays AI-free
   and unchanged. Needs consent prompts and graceful absence (`null`).
5. **Incident notebook → portfolio.** The handbook's five-line note (symptom, first wrong guess,
   evidence, fix, check first) as a form after every drill and lab room; saved locally; export as
   Markdown. Feeds the job-search unlock: real notes are interview material.
6. **New module + drills: "AI in operations".** How to use an AI assistant during an incident
   safely: read-only first, approval before any change, evidence-bound answers, never paste secrets,
   prompt injection from logs/tickets. 2026 role trend: the engineer supervises agents. One drill
   where an agent proposes a risky restart.
7. **Own mini-widgets where no free tool exists** (9 Nov Linux research): load-average simulator,
   boot-process stepper (firmware → GRUB → kernel → initramfs → systemd), systemd OnCalendar
   explainer with next runs, sudoers line explainer, LVM visualiser. Small, offline, in the page.
8. **Small UX:** unmet-prerequisite hint in the map panel; a "30 minutes today" button (one study
   item + one drill + five review cards); table readability pass (already on the list).
9. **Maintenance:** a link-health script (`research/check_links.py`) run monthly over practice.json
   and roadmap.json (three sites changed status within one month); multi-file artifact so the
   claude.ai copy can pass 16 MB (shell page + data files); platform topics check (Backstage,
   FinOps/OpenCost, GitOps with Flux now have free practice).

## Incident backlog from the 10 Nov search (for lab rooms and drills)

How to read this: the search results below are summaries. Before a room or drill is written, its
source must be opened and read in full (project rule), and community-reported, not the user's own.
A grep on 10 Nov showed the handbook ALREADY explains most of these in modules 23–31 and 41–51, so
the gap is hands-on practice, not text. "NEW" marks what the handbook does not have yet.

### A. "Why does this machine take so long to boot?" (the user's question)
Method first: `systemd-analyze`, `systemd-analyze blame`, `systemd-analyze critical-chain`.
| Cause | Sign | Fix | In handbook? | Source |
|---|---|---|---|---|
| A disk in /etc/fstab that is missing | "A start job is running for dev-disk-by-uuid…" for 1 min 30 s (systemd's 90 s default) | `nofail` (and `x-systemd.device-timeout=`), test with `mount -a` | yes (41, 23, 27) | dedoimedo.com/computers/ubuntu-beaver-slow-boot.html |
| Waiting for a network card that is unplugged or unused | "Wait for Network to be Configured" (`systemd-networkd-wait-online`) | `optional: true` in netplan, or limit the wait to one interface | yes (41 §3.5) | virtnet.bond doc on Ubuntu 24.04 |
| cloud-init probing for a cloud that is not there (bare metal / plain VM) | long cloud-init stage; Launchpad bug 2057763 was a ~2 min MAAS datasource timeout | `datasource_list: [ None ]`, or `/etc/cloud/cloud-init.disabled` | partly; NEW as a boot cause | bugs.launchpad.net/bugs/2057763 |
| NFS mount with the server down | boot stalls on the mount | `nofail,_netdev,x-systemd.automount` | check 41 §9 | lists.ubuntu.com/archives/ubuntu-users/2021-September/305094.html |
| Kubernetes/containerd installed on the host | kubelet, containerd and many pods start at boot; apps take minutes after boot | measure with critical-chain; `systemctl disable` what the host does not need; swap in fstab stops kubelet | NEW (matches the user's own experience) | github.com/awslabs/amazon-eks-ami/issues/1751 ; truenas.com/community/threads/…102778 |
→ **Idea:** one playbook section "Boot is slow: find the 90 seconds", plus a lab room (needs the VM tier for a real reboot; a container room can still use recorded `systemd-analyze` output and broken fstab/netplan files).

### B. Port clashes (like the user's Apache vs Dokploy case)
| Incident | Fix | In handbook? | Source |
|---|---|---|---|
| Port 53 taken by systemd-resolved's stub listener; Pi-hole/AdGuard/dnsmasq container cannot bind | `DNSStubListener=no`, or publish on one host IP only | yes (42, 28) | discourse.pi-hole.net/t/docker-unable-to-bind-to-port-53/45082 |
| k3s installs Traefik + ServiceLB and grabs 80/443 on every node; existing nginx/Apache collides | `--disable=traefik` AND `--disable=servicelb`, or move ports | NEW | docs.k3s.io/networking/networking-services ; community.traefik.io/t/…/30262 |
| Dokploy: 80/443/3000/8080 already in use at install; changing Traefik ports broke every route | find the owner with `ss -ltnp`; see issues | yes for 80/443 (21, 45); 8080 case NEW | github.com/Dokploy/dokploy/issues/804 , /3806 |
→ **Idea:** room "Who owns port 53/80/443?" in three variants (resolved, Apache, a stale docker-proxy).

| Incident | Fix | In handbook? | Source |
|---|---|---|---|

## How people practise without a subscription or a production machine
(The user asked for this; verify free limits on the official pages before adding to module 54.)
| Way | What it gives | Cost / caution |
|---|---|---|
| **Local VMs with snapshots** (Multipass, VirtualBox/Vagrant, KVM) | a real Ubuntu you can break, snapshot and roll back | free; needs RAM and ~50 GB disk |
| **Kubernetes in Docker** (kind, k3d, minikube) | multi-node clusters on a laptop, deleted in one command | free |
| **BrokenOps** (github.com/HimanM/BrokenOps) — NEW find | self-hosted: spins up deliberately broken VMs with checks, on KVM/libvirt | free, open source; UNVERIFIED and it runs someone else's scripts as root → only on a throwaway machine, never the user's main one |
| **grokdevops linux-triage** — NEW find | a setup script builds a broken environment under /tmp to fix | free; same caution |
| **PLUG / reesebuilt linux-datacenter-lab** | lab courses on one Linux host with snapshots | free |
| **Oracle Cloud Always Free** | 4 ARM cores + 24 GB RAM claimed "forever" in guides | needs a card to sign up; idle instances may be reclaimed |
| **Azure for Students** | free services, no card | full-time university students only |
| **Browser playgrounds** (Killercoda, iximiuz, KodeKloud, Cloud Shell, Codespaces) | already in the handbook's no-VM ladder | time-limited |
| **The handbook's own Labs** | disposable Ubuntu with checks, on Docker | free, local |

**The idea this points to:** the handbook's Labs are the same pattern as SadServers/BrokenOps
(a broken machine + a check script), but free, offline and safe by design. So the strongest
enhancement is still #1: write L1–L2 rooms for groups A–E above, starting with the ones that need
no VM tier (B port clashes, D dockerizing basics need nested Docker → VM tier; A boot needs VM
tier for the reboot itself; config-only variants work in the container).
